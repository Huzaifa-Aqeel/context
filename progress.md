Last reviewed: 2026-10-09. Update this file after each substantial implementation. This is the active handoff; detailed pre-FR_v2 checkpoints are preserved locally in `docs/archive/progress-through-checkpoint-54.md`.

## Source of truth

- `FR_v2.md` governs current product behavior. `FR.md`, `FR-audit.md`, `tech_stack.md`, `implementation-plan.md`, and `qloo audit.md` describe earlier decisions or evaluations and must not override FR_v2.
- Context is one blind-first Expo iOS/Android assistant. Home retains its two horizontal tabs, one Capture a scene button for all photo use cases, Choose a photo, Continue when available, and Ask Context. Do not create separate workflow buttons or screens for books, games, or events.
- Priority flows: book shelf, game shelf, physical event material, and nearby dining by voice without a photo. Personalized Area Discovery is a complementary fifth flow; general scene analysis is secondary. A signed, uniquely Qloo-resolved interest is required before Capture or Ask Context. The inner My taste profile switch chooses edit versus replacement setup; Location and Scene speech switches remain in Personalization.
- Before Qloo web search, inspect `qloo-hackathon-kit-main/`. Never print credentials, persist precise coordinates/images/conversation by default, or fabricate facts or cultural relationships. `.env.local` is private and gitignored.

## Current place-flow implementation (2026-10-09)

- Geoapify now replaces Google Places for exact public/named anchors, Qloo-place identity cross-checks, practical details, active-device reverse geocoding, and the optional `walk_10` contour. The existing Event capture/Ask and Calendar behavior remain; Event-only Tavily research remains. Dining and Area Discovery never call Tavily. `GEOAPIFY_API_KEY` is the documented environment name; the local lower-case `geoapify_api_key` is also read without exposing it.
- Dining uses one Qloo restaurant-tagged Insights pool at 2 km, expanding once to 5 km, then checks up to five ranked candidates with Geoapify to speak a primary and at most one alternative. A Qloo result missing from Geoapify stays eligible with practical facts explicitly unverified; contradictory identity is skipped. A DEVICE anchor rounds coordinates only for Qloo; precise foreground coordinates remain session-only for physical calculations. Event venue and named-place anchors are resolved with Geoapify and never silently replaced by device position. The optional Event performer signal is temporary and used only when the user asks for dining that fits the show.
- Area Discovery uses one global Qloo cross-category ranking at 800 m (one expansion to 2 km if empty), plus at most two sequential category top-ups if diversity is insufficient. Up to three different categories are spoken. Geoapify only validates/enriches Qloo picks. Area Session retains ranking, matches, presented IDs, anchor, orientation, and optional walking geometry for follow-ups. “What else?” validates the next place instead of treating a Qloo suggestion as a confirmed public POI. A mall request uses mapped Geoapify building POIs as a bounded candidate set, typed Qloo Search, then one restricted Qloo Insights ranking; sparse mapped POIs are reported honestly.
- Active-scene Qwen routing is reused for Event, Dining, Area, named anchors, mall, and practical POI requests. Event research remains available; place requests cannot route to Tavily. The existing Home, Personalization, Capture, and Ask Context UI controls were preserved. `FR_v2.md` was updated with the provider boundary, five-flow scope, place session/failure/privacy behavior, and app-wide Qloo contributor wording.
- Geoapify responses are no longer cached across server requests; scene/session state retains reusable place evidence without freezing time-sensitive hours. An explicit dining time is interpreted in the anchor timezone, and simple weekly Geoapify hours are checked conservatively. Complex/unparseable hours, a missing venue timezone, or an ambiguous AM/PM remain unknown. The Area initial answer states when all practical details are unverified; “What else?” validates the next Qloo candidate and skips contradictory identities. Practical POIs without a mapped name get a category label. An active Event/Dining/Area conversation no longer triggers an unnecessary device-location read for a scene-relative request; an explicit near-me request still does.
- Bounded live checks confirmed Geoapify venue resolution and a restaurant POI match/details, Qloo restaurant category filtering, and a cross-category Qloo Area ranking. Final `npm run check` passed TypeScript, lint, and all 212 offline tests; native Expo export bundled both iOS and Android. No Vision, Whisper, TTS, Calendar, or device calls were made for this place-flow implementation.
- Remaining validation: test a complete Event/Dining/Area conversation on a physical phone; validate OS Calendar and foreground location permission there. Geoapify `building.places` returned only the mall itself for one live example, so the mall flow may honestly have too few mapped businesses. Complex or missing opening-hours data remain unknown.

## Earlier implementation checkpoints (historical)

- Event and Dining Ask now have a scene-first structured Qwen decision path (`lib/ai/scene-decision.ts`, `lib/orchestration/scene-ask.ts`). The signed active Event/Dining scene is routed before global dining intent; the model sees bounded scene facts, Qloo ranking, checked sources, cached Places facts, the exact question, and available capabilities, but not precise device coordinates. It selects an answer, clarification, scoped investigation, or explicit Calendar intent. Application code validates cited evidence IDs, visible/Qloo targets, location anchors, and the Calendar request before executing. Venue-anchored dining may resolve the venue through Places and then rank dining through Qloo; a second constrained Qwen call synthesizes retrieved facts when needed. The Book/Game display path is unchanged.
- Dining can use a uniquely resolved event venue as its anchor without requesting device location. A request explicitly near the user starts a new device-anchored dining session. Qloo remains the dining ranking provider; Places only resolves the event venue and practical details. Dining recommendations and checked place details are retained in active scene memory. The Location switch no longer erases event-venue dining, while device-anchored dining is cleared when switched off. Initial scene/dining answers already give the obvious orientation; Ask is for the user's specific follow-up, not a required relay for basic facts. The model prompt excludes generic attendance verdicts.
- Dining candidates are explicitly sorted by Qloo affinity before selecting the primary and alternative, rather than assuming Qloo response order; no numeric affinity is spoken. Event Capture now names up to two printed performers when Qloo taste ranking is unavailable, so basic event orientation remains in the first answer.
- Calendar creation now requests read/write calendar permission, guards concurrent identical requests, and checks the selected calendar for a matching title/start before creating a duplicate. This is guarded in app code, not model output. Navigation, URL opening, and dialing remain unavailable. `FR_v2.md` reflects these product decisions.

- Existing Expo Router app, configurable vision/reasoning providers, Qloo general-scene grounding, camera/photo pipeline, accessible scene text, one-orb voice input, Whisper transcription, Orpheus speech, and scene-only auto-speak toggle remain in place. Photo preparation preserves pixel dimensions. Qloo and visual evidence are separated; named but unresolved visual references remain visible.
- Required-profile foundation is complete in the app and main scene APIs. Home's existing entry points open My Interests when no signed match exists; direct camera/scene/conversation routes show the setup gate. A no-match onboarding response does not save a usable profile. Deleting all matched interests returns to the gate.
- Local versioned preferences persist the signed Qloo profile, grouped interests, Location switch, Scene speech switch, and speech preferences. Image, scene, locality, precise location, and conversation remain session-only. A new capture preserves preferences. Local `.env.local` has a stable `SESSION_SIGNING_KEY`; deployment must configure its own stable private value.
- Current old general-scene orchestration and prior semantic regression harness remain functional while the new priority flows are built. Do not mistake those old tests for FR_v2 acceptance.
- Shared cultural-display engine: books and games are the two enabled categories in `lib/display/categories.ts`, which defines Vision scene instructions, Qloo type, identity rule, spoken item label, brief fields, and question-field checks. Generic display orchestration lives in `lib/orchestration/display*.ts`; the registry routes Vision, Qloo resolution/ranking, and Qwen brief field selection. New safe fact keys require only an adapter entry because the shared schema validates key syntax and the brief builder filters by each category's allowed fields. A new comparable Qloo-supported display category can be added without another parallel pipeline or UI button. The signed scene still uses the legacy `shelf` key and cache signing label for existing scene compatibility. Vision requests a compact title/author or title/platform inventory; its timeout is 60 seconds. Typed Search uses a shared serial queue with bounded 429 retries, then one Insights POST ranks returned visible IDs. Book matching uses author when supplied and also serves Personalization. A signed device-local ID cache skips repeat Search. Unresolved and omitted candidates remain visible, and partial ranking yields up to four shortlisted items.
- Display Capture makes no Tavily call. The independently configurable display role uses Qwen Max for **one** call that gives known book broad categories/specific genres or game genres for the entire visible inventory, while preparing deeper brief facts only for the 1–4 Qloo-shortlisted items. It runs even with no Qloo shortlist. Labels are stored as `MODEL`, and uncertain labels remain unknown. `DISPLAY_*` configuration takes precedence over legacy `SHELF_*`; the existing private `SHELF_MODEL` remains valid. Reasoning is enabled for the brief, not Vision or ordinary Ask. The initial result now names **every** confidently read book/game title with its known category/genre, then adds supported taste relevance; it has no arbitrary title or line cutoff and does not expose affinity scores. Display Ask answers deterministic inventory, membership, packaging platform, rank, and known co-op facts from scene memory. If another question is clearly answered by the saved brief, it uses one Qwen answer call. An absent field, changing fact, or Qwen `needsResearch` result triggers bounded Tavily search scoped to visible title(s) and the exact question, followed by source-constrained Qwen synthesis. Relevant source snippets and checked answer are retained in active scene memory with a freshness window; missing or uncited sources leave the answer unknown. No generic locality/Places router is involved. A profile change reranks confirmed IDs and rebuilds the brief without another Vision/Search pass.
- Event capture uses a dedicated printed-event Vision contract and deterministic Event Scene Memory. It retains all readable performer names, printed schedule entries, printed end time, and important public details such as admission, doors time, age limits, or accessibility notes. The first answer reads these printed facts without a two-name cutoff before any supported Qloo taste connection. Typed Qloo Search resolves supported named references; one Insights batch per returned entity type ranks the visible references against Personalization. Capture invokes no Tavily, location, Places, Calendar, or second synthesis call. Event Ask reuses printed time/performers/ranking and other printed details, investigates only named pairs on demand, researches current facts through Tavily on demand with session cache, and obtains exact venue details from Google Places only for practical questions. A changed profile reranks confirmed visible IDs without another Search. No map, navigation, or external-link opening action exists.
- Calendar actions use the existing Ask Context orb. They require an explicit request and an absolute date with year, start time, and timezone from the printed material or official-source research; otherwise the voice flow asks for the missing details. If no printed end time is available, Context asks for an end time and offers “use one hour.” It creates the native event only after the user answers, marks a chosen one-hour end as a placeholder, and adds an explicit reminder offset when requested. The Expo Calendar plugin is installed and configured; native behavior has not yet been device-verified.
- Voice-only dining asks for one foreground position only after an explicit nearby-dining request and enabled Location. Qloo Insights ranks restaurant-tagged places within 2 km, expanding once to 5 km if needed. At most two Qloo-ranked candidates enter session memory; Google Places can add exact address/phone/current-open details on demand, but never reorder candidates. The optional Places key is not configured yet, so the Qloo discovery path works while practical details degrade honestly. Precise position is session-only and is cleared when Location is turned off or the dining session is replaced.
- The scene screen now excludes event/dining scenes from its older general-scene Taste Evidence effect. This prevents an extra Qloo taste request and keeps the event's deterministic summary and stored ranking intact. Ask Context copy is contextual for shelves, events, dining, and general scenes without adding controls.
