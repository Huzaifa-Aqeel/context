## Named-category nearby help (2026-10-11)

- Current product decision supersedes the older Qloo Area Discovery and two-phrase-only Dining notes below. Every new nearby request names a category. Broad “what is worth seeing nearby?” requests ask for a category and do not start a Qloo/Geoapify search. The old cross-category Area implementation remains in code for compatibility with existing scene data but is not reachable as a new discovery workflow.
- Restaurant, bar, and the original “somewhere I’d enjoy eating” phrasing share the unchanged Qloo restaurant-tagged ranking and initial answer; returned cuisine/category identifies each place. Bar phrasing is not a bar-only Qloo filter. Geoapify still resolves a named anchor and fills missing individual practical details on demand, never the initial Qloo candidate list.
- Bookstore, record store, game shop, pharmacy, ATM, and restroom searches use Geoapify only. A bounded proximity search orders mapped candidates by straight-line distance, expands its radius only when empty, and fetches Place Details for the closest result. The answer names the place, available address, straight-line distance from the chosen anchor, and listed open/closed status only when current evidence and timezone support it; otherwise opening status stays unknown. These are not taste recommendations.
- Home/capture guidance, README, and `FR_v2.md` now present one category-specific nearby use case rather than separate Dining and broad Area use cases. `npm run check` passed TypeScript, lint, and all 244 offline tests; `git diff --check` passed. A bounded live Geoapify bookstore lookup around a public New York coordinate returned five mapped results; the closest result had an address, coordinates, Place Details opening hours, and timezone, and the hours parser established a current listed status. Other categories, device speech, and accessibility still need end-to-end validation.
